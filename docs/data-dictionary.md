# Data dictionary — synthetic 8-system world

**All data in this repository is synthetic.** Every provider, member, claim, address,
phone number, NPI and TIN below is generated by `data/generate_world.py` from a seed.
No real person, no real claim and no employer-internal system appears anywhere. The
eight source systems are referred to **only by class** (CLAUDE.md hard rules 1 and 2):
`ticketing`, `ops_workflow`, `crm`, `claims_a`, `claims_b`, `credentialing`,
`analytics_lake`, `finance_mart`.

## Regenerating

```bash
uv run python data/generate_world.py --seed 42 --out data/extracts
```

Writes eight `data/extracts/{system}.jsonl` files and three ground-truth artifacts to
`data/ground_truth/`. The run is **deterministic**: one `random.Random(seed)` is created
in `build_world()` and threaded through world building and then through every extract
writer, dictionaries are iterated in insertion order and nothing iterates a set — the
same seed reproduces byte-identical files.

Changing the generator means regenerating the extracts *and* the ground truth, and
re-running the ER/detection evals, whose numbers will shift.

## The true world (`pipeline/worldgen/world.py`)

`build_world(seed)` produces the truth; the extract writers then tell it eight
inconsistent ways. Nothing in the extracts contradicts the world — systems omit,
re-shape and re-name, but never lie about an identifier (see *NPI integrity* below).

| Object | Key fields |
|---|---|
| `TrueProvider` | `entity_id` (`P-0001`), `npi`, `tin`, `legal_name`, `dba_name`, `specialty`, `market`, `address` (current), `prior_address` (movers only), `phone`, `is_org`, `panel` (member_ids), `monthly_baseline` (claim lines/month, 15–40) |
| `TrueMember` | `entity_id` (`M-000001`), `member_id` (`MB########`), `name`, `dob` |
| `ClaimEvent` | `provider_id` (true `P-…`), `member_id`, `system`, `month`, `code`, `units`, `billed`, `allowed`, `paid`, `denied`, `denial_reason` |
| `Anomaly` | `entity_id`, `signature`, `months`, `details` |
| `ERTrap` | `kind`, `entity_ids`, `note` |

**Money.** Every amount is a `Decimal` quantized to cents (`ROUND_HALF_UP`) and
serialized as a *string* in JSONL (`"265.50"`) so no float rounding can drift between
runs or languages. A denied line has `allowed = 0.00` and `paid = 0.00`; the billed
amount stands.

**Markets.** `MKT-ATX` Austin TX, `MKT-DFW` Dallas-Fort Worth TX, `MKT-PHX` Phoenix AZ,
`MKT-DEN` Denver CO, `MKT-MSP` Minneapolis-St Paul MN, `MKT-CLT` Charlotte NC. Providers
are assigned round-robin, so each market holds 26–27 providers.

**Codes.** Twelve behavioral-health CPT/HCPCS codes with invented unit prices:

| Code | Description | Unit price |
|---|---|---:|
| 90791 | Psychiatric diagnostic evaluation | 180.00 |
| 90792 | Psychiatric diagnostic evaluation with medical services | 220.00 |
| 90832 | Psychotherapy, 30 minutes | 75.00 |
| 90834 | Psychotherapy, 45 minutes | 110.00 |
| 90837 | Psychotherapy, 60 minutes | 160.00 |
| 90839 | Psychotherapy for crisis, first 60 minutes | 195.00 |
| 90846 | Family psychotherapy without patient present | 125.00 |
| 90847 | Family psychotherapy with patient present | 135.00 |
| 90853 | Group psychotherapy | 45.00 |
| 96130 | Psychological testing evaluation, first hour | 145.00 |
| H0004 | Behavioral health counseling and therapy, per 15 min | 28.50 |
| H2019 | Therapeutic behavioral services, per 15 min | 32.75 |

`H0004` and `H2019` are timed codes and legitimately carry `units` of 2–8; every other
code bills 1 unit per line (the one exception is the `impossible_volume` signature, see
below). The two highest-priced codes — **90792** and **90839** — are the drift target.

**Which claims platform.** Providers in `MKT-ATX` / `MKT-DFW` / `MKT-PHX` adjudicate on
`claims_a`, the other three markets on `claims_b`. A further ~10% of providers (21 at
seed 42) bill on **both** platforms, so cross-platform resolution has real work to do.

## Per-system extracts

Every file is JSONL, one record per line, LF-terminated, keys in the order listed.

### `ticketing.jsonl` — provider-service tickets

~1.5 tickets per provider per quarter, ordered by `opened_at`.

| Field | Type | Notes |
|---|---|---|
| `ticket_id` | str | `TKT-#####` |
| `opened_at` | str | ISO timestamp, `2025-01-01T07:41:41` |
| `provider_name` | str | **free text**, a name *variant* — not the legal name |
| `provider_npi` | str \| null | present ~60% of the time; **never** for the `name_variants_no_npi` trap providers |
| `category` | str | e.g. `claim status inquiry`, `roster update` |
| `status` | str | `open` \| `pending` \| `resolved` \| `closed` |
| `description` | str | one-line free text consistent with `category` |

### `ops_workflow.jsonl` — network-operations requests

~0.5 requests per provider per quarter. **No NPI field at all** — name plus market is the
only handle, which is the hardest resolution case in the world.

| Field | Type | Notes |
|---|---|---|
| `request_id` | str | `OPS-####` |
| `provider_name` | str | free-text variant |
| `market` | str | `MKT-…` |
| `request_type` | str | e.g. `panel roster refresh`, `contract amendment` |
| `month` | str | `2025-01` |
| `status` | str | `submitted` \| `in_review` \| `approved` \| `rejected` \| `completed` |

## Identity-mess rules

What each system does to a provider's identity:

| System | Provider handle | Name form | Address |
|---|---|---|---|
| `ticketing` | free text + NPI 60% | variant | — |
| `ops_workflow` | free text only | variant | — |
| `crm` | `ACC-####` + NPI 60% | DBA or variant | current |
| `claims_a` | `PA-####` + NPI | — | — |
| `claims_b` | `PB-####` + NPI | — | — |
| `credentialing` | `CRD-####` + NPI + TIN | legal | stale for movers |
| `analytics_lake` | NPI | — | — |
| `finance_mart` | TIN | legal (or DBA for trap providers) | — |

**Name variants.** A variant is one of: `First Last`, `Last, First`, `LAST, FIRST`,
`Dr. F. Last`, `First Last, CRED`, `First M. Last`, `Dr. First Last`, `first last`; for
organizations: legal name, DBA, `LEGAL NAME`, `L.L.C.`-punctuated, `DBA (Last)`,
`LAST CRED`. 2% of emitted names additionally pick up whitespace/punctuation noise
(doubled space, leading/trailing space, dropped comma, trailing period).

**System-local ids are sparse and unaligned.** Each system numbers providers in its own
shuffled order over a sparse range, so `P-0007` is *not* `ACC-0007` or `PA-0007`.
Alignment would make resolution trivial.

**NPI integrity — the one thing never corrupted.** A system either carries the true NPI
or omits it. There are no wrong NPIs anywhere, by design: a corrupted identifier would
make the ground-truth crosswalk unlearnable rather than merely hard. Generated NPIs are
10 digits, start with 1 or 2, and carry a valid Luhn check digit over `"80840" + first
nine digits` (`catalog.is_valid_npi` verifies this).

## Anomaly signatures (`data/ground_truth/anomalies.json`)

Twelve anomalous providers, three per signature, drawn from providers that are **not**
ER-trap providers so detection and resolution evals stay independent. Each entry is
`{entity_id, signature, months, details}`; `months` uses the same `2025-MM` format as
the claim ledger.

### `volume_spike` — months 2025-10 … 2025-12

Monthly volume jumps to 3–5× the provider's own baseline, with 70% of the inflated
volume concentrated in the provider's **market's top code** (the code carrying the most
billing weight across that market). At seed 42 the realized spike-vs-baseline ratios are
4.2×–5.1×. `details`: `market`, `focus_code`, `multiplier`,
`baseline_claims_per_month`, `focus_code_share_in_spike`.

### `denial_surge` — months 2025-09 … 2025-12

The provider's denial rate jumps from its ~8–16% baseline to 45–60%, concentrated on two
reasons (`CO-197 precertification or authorization absent`, `CO-16 claim lacks
information needed for adjudication`) rather than spread across the reason catalog.
Denials are applied as an exact count per month, not a per-line coin flip, so the
injected rate is a fact the eval can rely on. `details`: `baseline_denial_rate`,
`surge_denial_rate`, `concentrated_reasons`.

### `code_mix_drift` — months 2025-07 … 2025-12

From month 7 onward the provider shifts 60–75% of its billing onto the two
highest-priced codes (90792, 90839), up from a baseline share of 6–16%. Volume and
denial rate are unchanged — only the mix moves, which is what makes this signature
invisible to a volume-only detector. `details`: `target_codes`,
`baseline_high_price_share`, `drift_high_price_share`.

### `impossible_volume` — months 2025-08 … 2025-12

920–980 **units** of 90837 (a 60-minute psychotherapy session) per month — more than 40
sessions per working day, which is not physically possible — concentrated on a small set
of 4–6 members. This block is billed *on top of* the provider's normal activity, so the
realized monthly peak is ~1,010–1,045 units against a non-affected peak of ~60–80.

> **Design decision.** The phantom block is emitted as ~270 lines of 3–4 units each
> rather than ~950 single-unit lines. The signature is defined in *units* (the spec's
> ">900 units of 90837"), multi-unit lines on a per-session code are themselves a
> billing red flag, and single-unit emission would have pushed the corpus past 67k claim
> lines and the extracts past 20 MB. Detection reads `unit_count`, which is unaffected.

## Entity-resolution traps (`data/ground_truth/er_traps.json`)

Deliberate wrong-merge bait. CLAUDE.md hard rule 4 makes a wrong merge a CI hard-fail;
this registry lets the eval report not just "zero wrong merges" but "zero wrong merges
*on the pairs designed to cause them*". Trap providers are disjoint from anomalous ones.

| Kind | Count | What it does |
|---|---:|---|
| `same_name_distinct` | 3 pairs (6 providers) | Two **distinct** providers share a last name and a first initial in **different markets** (e.g. Anita Mbeki in `MKT-ATX` vs Arjun Mbeki in `MKT-CLT`). Different NPIs, TINs, panels and activity. Merging either pair is the unsafe error. |
| `name_variants_no_npi` | 4 providers | CRM and ticketing carry **no NPI at all** and only divergent free-text shapes (`Dr. A. Sharma` / `SHARMA, ANITA` / `Anita Sharma, MD`, DBA `A. Sharma LLC`). Claims, credentialing and analytics still carry the true NPI, so the correct merge is reachable — but only through contextual evidence. |
| `stale_address` | 3 providers | The provider relocated within their market. Credentialing kept the **old** address; CRM has the new one. Address similarity argues DISTINCT when the truth is the same entity. |
| `dba_payee` | 2 providers | `finance_mart` pays the TIN under the provider's **DBA**, while credentialing holds the legal name — the TIN is the only bridge. |

Accidental near-collisions also occur naturally: 160 providers are drawn from 30 first
names and 26 last names, so shared surnames are common. That is realistic messiness, and
the crosswalk remains the referee for all of it.

## Ground-truth crosswalk (`data/ground_truth/crosswalk.csv`)

Columns: `system,local_id,entity_kind,entity_id`.

One row for every system-local identifier emitted anywhere in the eight extracts.

| `entity_kind` | Systems | `local_id` is |
|---|---|---|
| `provider` | `crm`, `claims_a`, `claims_b`, `credentialing`, `analytics_lake`, `finance_mart` | that system's own provider identifier: `ACC-####`, `PA-####`, `PB-####`, `CRD-####`, the NPI, the TIN |
| `provider_ref` | `ticketing`, `ops_workflow` | the ticket/request id — these systems reference a provider only as free text, so the *record* is the unit of resolution |
| `member` | `claims_a`, `claims_b` | the `member_id` appearing on that platform's claim lines |

At seed 42: 6,371 rows — 160 provider rows each for crm, credentialing, analytics_lake
and finance_mart, 88 for claims_a and 93 for claims_b (only providers who actually
billed there), 959 ticketing and 317 ops_workflow provider references, and 2,112 +
2,162 member rows. Members whose panel membership never produced a claim line appear in
neither claims system and so have no crosswalk row.
